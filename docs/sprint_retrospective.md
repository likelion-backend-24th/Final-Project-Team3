Sprint Retrospective는 팀의 사람·협업·프로세스·도구·공통 완료 기준을 돌아보고 품질과 효과성을 높일 개선을 선택하는 자리입니다. 제품에 관한 결정은 Sprint1  Review , 별도 품질평가는 Week 4 별도 품질평가 문서에서 담당합니다.

## 회고

| Sprint | Keep | Problem·학습 | Try | 영역 |
| --- | --- | --- | --- | --- |
| Sprint 1 | 실제 계정으로 스모크 테스트하며 개발한 것 | 데모 시나리오 순서가 실제 유저 흐름과 달라서 전달력이 떨어짐 | 다음 데모 전 시나리오를 실제 유저 여정을 기준으로 순서 재구성 | 프로세스 |
| Sprint 2 | 문서(요구사항·API·ERD·권한매트릭스) 변경 사항을 작업 착수 전에 매번 대조해 스테일 참조·번호 꼬임을 여러 번 잡아낸 것 | 이슈 트래커 확인 없이 같은 Task 범위를 중복으로 작업하는 사례가 발생함 / PR에 설명 없이 올려서 이슈가 자동으로 안 닫히는 경우가 반복됨 | 작업 착수 전 GitHub 이슈의 담당자·상태를 확인하는 것을 습관화 / PR 본문에 "Closes #N"을 항상 포함 | 프로세스 |
