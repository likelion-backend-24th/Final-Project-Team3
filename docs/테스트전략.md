- 안전한 사용자 결과와 저장되지 않아야 할 데이터: 이메일 중복은 409로 거부되고 계정이 생성되지 않는다, 정원 조회 실패 시 503으로 거부되고 홀드가 생성되지 않는다(Fail-closed), 순번 미도달 결제 요청은 거부되고 좌석이 확정되지 않는다
- 복구·재시도 기준: 다른 이메일로 재가입 또는 로그인 유도, 클라이언트 재시도 안내, 순번 도달까지 폴링 대기
- 관련 Test·Evidence: MemberSignupLoginTest, CapacityContractFailureTest, WaitingQueueTest
- 상태: DONE — Sprint1 데모 완료, 강사·멘토 피드백 완료

## **부하 테스트 (Sprint 3)**

k6로 진행. 스크립트는 저장소 `infra/loadtest/`(로컬 전용, 커밋 여부는 팀 논의 필요).

### **정합성 테스트**

**방법**: 정원 100인 세션 1개에 서로 다른 사용자 1,000명이 동시에 신청(HOLD 요청).

**통과 기준**: HOLD 수 = 정원, 나머지는 QUEUED, 순번 중복·누락 0, 5xx 0, 종료 후 DB의 `current_active` ≤ 정원.

**스크립트**: `infra/loadtest/test1-consistency.mjs` (+ `verify1.sql`, `reset1.sql`)

| **항목** | **1차(버그 있음)** | **중간(제약만 추가)** | **최종(수정 후)** |
| --- | --- | --- | --- |
| HOLD 수 | 100 | 100 | 100 |
| QUEUED 수 | 900 | 91 | 900 |
| 대기 순번 중복 | 810건 | 0건 | 0건 |
| 대기 순번 누락 | 810건 | 0건 | 0건 |
| 5xx 에러 | 0건 | 809건 | 0건 |
| current_active (DB) | - | - | 100 (≤ 정원) |
| 응답시간 | p50 10.5s / p95 16.1s | - | p50 10.0s / p95 15.4s |

**발견한 버그(root cause)**: `waiting_queue`에 `(session_id, position)` 유니크 제약이 없어서, "현재 최대 순번 + 1"(read-then-write) 방식이 900명 경쟁 상황에서 경쟁 상태에 걸려 같은 순번이 여러 명에게 중복 배정됨.

**중간 시도의 부작용**: 유니크 제약만 추가하니 중복은 사라졌지만, 재시도 5회로는 900명 경쟁을 못 버텨서 809건이 500 에러로 실패함(재시도 소진).

**최종 수정**: `session_capacity_lock`에 이미 쓰던 원자적 UPDATE 패턴을 대기열 순번에도 적용(`queue_position_counter` 테이블 신설) — 재시도 자체가 필요 없어져서 중복도 실패도 0건.

**한 줄 요약**: 정원 100, 동시 신청 1,000건 → 수정 전 순번 810건 중복(FAIL) → 수정 후 중복·누락 0, 5xx 0(PASS).

**관련 PR**: #231 (fix/waiting-queue-position-race)

### **처리량 한계 테스트**

**방법**: 초당 요청 수(RPS)를 10 → 50 → 100 → 200으로 단계적으로 올림(k6 `ramping-arrival-rate`, 단계당 25초).

**통과 기준**: p95 응답시간 ≤ 500ms, 에러율 ≤ 1%(임의 기준).

**대상**: 정원이 아주 큰 세션 1개 — 정원 병목이나 락 경합(핫스팟 테스트의 관심사)이 섞이지 않게 하기 위함.

**스크립트**: `infra/loadtest/test2-throughput.js`

| **단계** | **p95 응답시간** | **에러율** | **판정** |
| --- | --- | --- | --- |
| 10 RPS | 72ms | 0% | PASS |
| 50 RPS | 3.42s | 0% | FAIL (지연 기준 초과) |
| 100 RPS | 14.26s | 0% | FAIL |
| 200 RPS | 18.1s | 0% | FAIL |

**처리량 한계: 10 RPS와 50 RPS 사이.** 10 RPS까지는 72ms로 빠르다가 50 RPS부터 p95가 3.4초로 급격히 튀고 그 뒤로 계속 악화됨. 에러율은 끝까지 0%였는데, 요청이 실패한 게 아니라 "느리게라도 결국 성공"했기 때문 — 사용자 입장에서는 몇 초~십수 초를 기다리는 셈이라 사실상 타임아웃과 다름없음. dropped_iterations(k6가 VU 부족으로 아예 못 쏜 요청)도 3,273건 발생 — 서버가 감당 못 해서 요청이 쌓이고 있다는 신호.

**원인 추정**: `application.yaml`에 HikariCP 커넥션 풀 설정이 없어 기본값(10개)을 씀. 세션 락(`session_capacity_lock`) 경합이 아니라(핫스팟 테스트에서 락 경합의 영향은 따로 측정) DB 커넥션 풀 고갈이 먼저 병목이 됐을 가능성이 큼 — 커넥션 10개로 50 RPS를 처리하려면 요청마다 커넥션을 평균 0.2초 안에 반납해야 하는데 그게 안 되는 것으로 보임. 확정하려면 `maximum-pool-size`를 늘려서 같은 테스트를 재실행해 비교해야 함.

**상태**: 완료. **HikariCP 풀 크기 튜닝·재측정은 후속 과제로 남김(미수정)**.

### **핫스팟 vs 분산 테스트**

**방법**: 총 요청 수는 동일하게 두고, 세션 1개에 몰았을 때(핫스팟)와 세션 20개에 나눴을 때(분산)를 비교(k6 `shared-iterations`, 총 2,000건 · VUs 50).

**통과 기준**: 락 경합이 성능에 미치는 영향을 수치로 비교(핫스팟의 p95·처리시간이 분산보다 유의미하게 느려야 "락 경합이 실제로 비용"이라는 게 증명됨).

**원리**: `session_capacity_lock`은 세션당 행 1개 — 핫스팟은 그 한 행에 모든 요청이 원자적 UPDATE로 몰려 경합하고, 분산은 서로 다른 행이라 경합이 없음.

**스크립트**: `infra/loadtest/test3-hotspot-vs-spread.js`

| **항목** | **핫스팟(세션 1개)** | **분산(세션 20개)** | **차이** |
| --- | --- | --- | --- |
| 총 소요 시간 | 46.6초 | 22.0초 | 분산이 2.1배 빠름 |
| 평균 응답시간 | 1.13s | 534ms | 분산이 53% 감소 |
| p95 응답시간 | 1.65s | 1.04s | 분산이 37% 감소 |
| 처리량 | 42.9 iters/s | 91.1 iters/s | 분산이 2.1배 |
| 에러율 | 0% | 0% | 동일(둘 다 성공은 함) |

**락 경합이 성능에 미치는 영향이 수치로 확인됨.** `session_capacity_lock`은 세션당 행 1개라, 같은 세션에 몰리면(핫스팟) 그 한 행에 대한 원자적 UPDATE가 직렬화되면서 대기 줄이 생기고, 20개 세션에 나누면(분산) 서로 다른 행이라 병렬로 처리됨. 요청 수·VU 수가 완전히 같은데도 분산이 2배 이상 빠른 건 이 행 잠금 경합 때문.

**한 줄 요약**: 같은 2,000건, 같은 조건에서 세션 1개에 몰리면 46.6초, 20개에 나누면 22.0초 — 인기 세션 쏠림이 실제로 시스템 처리량을 절반으로 깎는다는 걸 수치로 증명.

**상태**: 완료, 수정 불필요(정확성을 지키기 위한 설계상 정상 동작).
