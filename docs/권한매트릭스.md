## 판정 순서

1. 인증 유효성
2. Role
3. Resource 존재와 소유 관계
4. 업무 상태
5. Dependency 결과
6. 허용 또는 안전한 실패

민감 Resource는 추측 방지를 위해 `404`를 선택할 수 있으며 근거를 기록합니다. `getConference`가 해당 — 미승인 컨퍼런스와 존재하지 않는 컨퍼런스를 구분하지 않고 동일하게 `404`로 응답해, 방문자가 "미승인 컨퍼런스가 존재한다"는 사실 자체를 추측하지 못하게 합니다.

Dependency 장애를 권한 없음으로 오인시키지 않습니다. 서비스 간 동기 호출이 Timeout·오류일 때는 `403`이 아니라 `503`으로 응답해 "권한이 없다"와 "지금 서비스가 응답하지 못한다"를 구분합니다(예: `createHold`의 `getSessionCapacity`, `getAttendeeSummary`의 `getAttendeeCheckinStats`, `getSettlement`의 `getPaymentSummary`, `getOperationStatus`의 `getSessionStatusSummary`, `withdraw`의 `getOrganizerWithdrawalEligibility`).

| `getAttendeeCheckinStats`/`getSessionStatusSummary`/`getPaymentSummary`/`getReviewsBySessionIds` | Reservation-Service | Conference-Service | `503`(참석자 통계는 캐시 있으면 캐시로 `200` 대체, 나머지는 즉시 `503`) |

이 구간은 Role 기반 판정이 아니라 "서비스 신원(내부 호출)"만으로 허용되며, 사람 사용자가 직접 호출할 경로가 Gateway에 없다는 전제로 인증을 생략한다. 감사·트레이싱은 Trace ID 전파로만 이루어진다(별도 내부 API 인증 토큰 없음 — 추후 강화 검토 대상).

## Sprint 3 이후 확인된 권한 로직 변경·유의사항

- **`OwnerScopeGuard`는 서비스별로 개별 구현**되어 있다 — Member-Service에는 재사용 가능한 유틸리티만 존재하고 실제로 호출하는 곳이 없으며(회원 자원은 본인만 다루므로 소유권 검증이 불필요한 구조), Conference-Service는 `OwnerScopeGuard.verify`, Reservation-Service는 서비스 메서드 내 직접 비교로 각각 구현한다.
- Conference-Service는 필터 체인에서 `GET /api/conferences/**`·`/api/sessions/**`·`/api/organizers/**`를 `permitAll`로 열어두지만, 그 하위 중 `ORGANIZER`/`ADMIN` 전용 GET(`getMyConferences` 등)은 컨트롤러의 `@PreAuthorize`가 별도로 적용되어 미인증 요청은 `401`이 아니라 `403`으로 응답한다(필터 통과 후 메서드 보안에서 걸리기 때문).
- **Member-Service의 관리자 회원조회(Task 18-4)는 `@PreAuthorize` 자체가 `@EnableMethodSecurity` 설정 누락으로 작동하지 않던 결함을 발견·수정하며 함께 배포됐다.** 즉 배포 전에는 `hasRole('ADMIN')` 검증이 조용히 무시될 수 있는 상태였음 — 권한 관련 신규 엔드포인트를 추가할 때는 `@EnableMethodSecurity` 활성화 여부를 반드시 함께 확인해야 한다는 교훈으로 기록.
- Reservation-Service의 `GET /api/qr-tickets/{reservationId}`는 로그인만 확인하고 **예약 소유자 검증을 하지 않는다** — reservationId를 아는 로그인 사용자라면 타인의 QR 티켓도 조회 가능한 상태로, 다음 보안 강화 대상으로 기록한다.
- `changeMemberRole`은 코드 레벨에서 Role 전이 제한이 없다(`MEMBER→ADMIN` 포함 모든 전이 허용) — 운영 절차(누가 언제 왜 권한을 바꿨는지)에 대한 감사 로그가 없다는 점과 함께 후속 검토 필요.
- 소셜 로그인(`socialLogin`/`linkSocialAccount`)은 코드 레벨에서 `role=MEMBER`만 생성하도록 고정되어 있어, [소셜로그인-참석자전용] 규칙이 "요청 거부"가 아니라 "애초에 다른 Role이 나올 경로가 없음"으로 보장된다.
- `getQueuePosition`·대기열 승격 관련 권한 판정(본인 소유 확인, `403`/`404` 구분)은 변경되지 않았으나, 응답에 포함되는 `estimatedWaitMinutes`의 산출 로직만 2026-09-28에 개선됨(결제 대기 좌석 만료 기준) — 권한 Matrix 관점에서는 별도 조치 불필요, `API·통합 계약` 문서 참고.
