## 결정 기록

| 결정 | 근거가 된 사용자 시나리오·위험 | 선택 | 검토 대안 | 결정 Sprint |
| --- | --- | --- | --- | --- |
| 모든 외부 요청은 Gateway를 단일 진입점으로 통과한다 | 전체 시나리오 공통 — 인증·CORS·Trace ID를 서비스마다 중복 구현하면 정책이 서비스별로 어긋날 위험 | Gateway 단일 진입점 + `/internal/**` 비공개 | 서비스별 직접 외부 노출 — 인증 로직 중복, CORS 관리 분산으로 기각 | Sprint 1 |
| JWT는 Gateway가 아니라 각 서비스가 직접 검증한다 |  Gateway를 무조건 신뢰하면, Gateway를 우회하거나 헤더가 위조됐을 때 다른 사용자로 행세할 수 있음 | 서비스별 JwtAuthenticationFilter가 공유 비밀키(HS256)로 매 요청 검증 | Gateway 일괄 검증 | Sprint 1 |
| CORS 대신 같은 출처(same-origin)로 서빙한다 | 프론트와 API를 Nginx 한 곳에서 서빙 | /api/ → Gateway 프록시 | 서비스별 CORS 설정 | Sprint 1 |
| 서비스별 DB를 완전히 분리하고 직접 DB 접근·JOIN을 금지한다 | [소유자원-접근제한] 규칙, 서비스 간 강결합 방지 | 서비스당 전용 DB, 논리적 ID(`memberId`·`conferenceId`·`reservationId`) 참조만 허용 | 공유 DB·직접 JOIN — 배포 독립성 상실, 한 서비스 스키마 변경이 전체에 영향을 주는 위험으로 기각 | Sprint 1 |
| Admin 전용 기능은 별도 오케스트레이션 서비스 없이 각 도메인 서비스가 직접 구현한다 | 강사님 피드백(“Admin이 필요하면 해당 서비스에서 엔드포인트 직접 제작”) — 별도 Admin-Service는 불필요한 홉과 배포 단위만 늘림 | Member-Service(회원 조회)·Conference-Service(승인/반려)가 각자 권한검증까지 직접 구현 | Admin-Service 오케스트레이션(Sprint 1 초기 결정) — 권한검증 중복·감사 어려움 우려로 도입했으나 실제로는 불필요한 서비스 간 홉만 추가한다고 판단해 철회 | Sprint 1 (재검토) |
| 서비스 간 동기 호출 실패 시 핵심 흐름은 Fail-closed로 처리한다 | [정원-초과-금지], [승인-전-비공개] — 실패 시 임의로 허용하면 정원 초과·미승인 노출 위험 | Timeout·오류 시 상태 변경·좌석 확정 안 함(신청 거부) | Fail-open(임의 성공 처리) — 데이터 정합성이 깨질 위험으로 기각 | Sprint 1 |
| 참고용 정보(예상 대기시간) 조회 실패는 Fail-open으로 처리한다 | 대기열 예상시간은 신청·결제를 막을 사유가 아님 | Conference-Service 장애 시 기본값 5분 사용 | 실패 시 대기열 조회 자체를 거부 — 참고 정보 때문에 핵심 흐름이 막혀 기각 | Sprint 3 |
| 세션 정원 검증은 신청 시점에 동기 API로 실시간 확인한다 | 시나리오 9·10, [정원-초과-금지] — 동시 신청 상황에서 최종 일관성만으로는 초과 판매 위험 | Reservation-Service → Conference-Service 동기 호출(세션 정원 조회 계약, Story 9 Task 9-2 `#23`) | 이벤트 기반 비동기 동기화(최종 일관성) — 동시성 상황에서 정원 초과 방지를 보장하기 어려워 기각 | Sprint 1 |
